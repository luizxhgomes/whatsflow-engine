# Story 1.2: Advanced Filters

## Status
InProgress

## Estimate
L (Large)

## Scope
**IN:** 12 filtros (tag, telefone, primeiro nome, sobrenome, nome completo, campanha, data inscricao, codigo area, ID usuario, campo personalizado, admin atribuido, etiqueta/label), colunas novas `assigned_to`/`campaign_id`/`source`, filter engine composable, UI popover + chips ativos, URL state
**OUT:** Filtros por sentimento IA, filtros por metricas de conversa (tempo resposta), exportacao de resultados filtrados, saved filters/presets

## Risks
- Performance com JOINs multi-tabela (contacts + contact_tags + campaigns) em scale — mitigacao: indices compostos, tags via subquery
- FK `campaign_id` referencia tabela `campaigns` que pode nao existir — mitigacao: verificar schema init, criar se necessario
- Complexidade UI com 12+ filtros simultaneos — mitigacao: componentes modulares, lazy rendering

## Story

**As a** operador do WhatsFlow,
**I want** filtrar conversas do Inbox por multiplos criterios (etiqueta/tag, telefone, nome, campanha, data de inscricao, codigo de area, campo personalizado, admin atribuido),
**so that** eu possa localizar rapidamente leads especificos e segmentar meu atendimento de forma eficiente.

## Acceptance Criteria

1. Coluna `assigned_to` (UUID, FK auth.users, nullable) adicionada em `inbox_conversations`
2. Coluna `campaign_id` (UUID, FK campaigns, nullable) adicionada em `inbox_conversations`
3. Coluna `source` (TEXT, enum: 'organic' | 'campaign' | 'flow' | 'manual', default 'organic') adicionada em `inbox_conversations`
4. Indices criados: `idx_conv_assigned_status`, `idx_conv_campaign`, `idx_contact_tags_tag`, `idx_contact_tags_contact`
5. API `GET /api/inbox/conversations` aceita novos query params: `tagIds`, `assignedTo`, `campaignId`, `phone`, `contactName`, `areaCode`, `createdAfter`, `createdBefore`, `customField`
6. Filter engine composable em `inbox-db.ts` aplica filtros via Supabase query builder com JOINs eficientes (tags via subquery, nao JOIN direto)
7. UI exibe icone de filtro (funil) na barra do Inbox que abre dropdown/popover com lista de filtros disponiveis
8. Cada filtro no dropdown expande para input especifico: tags (multi-select), telefone (text), nome (text), campanha (select), data (date range), area code (text), campo personalizado (key+value), admin (select)
9. Filtros ativos sao exibidos como chips/badges acima da lista de conversas, com opcao de remover individualmente ou limpar todos
10. Filtros sao combinados com AND (todos devem ser verdadeiros simultaneamente)
11. Performance: query com 3+ filtros ativos executa em < 500ms para 10K conversas
12. Estado dos filtros persiste na URL (query params) para compartilhamento/bookmark

## Dev Notes

### Arquitetura de Referencia
- **Filtros existentes:** `useConversations.ts` ja aceita `status`, `mode`, `labelId`, `search` — estender esse padrao
- **DB queries:** `inbox-db.ts` → `getConversations()` ja tem filtros composable com Supabase `.eq()`, `.ilike()` — adicionar novos
- **URL state:** Usar `useSearchParams` do Next.js App Router para persistir filtros na URL
- **UI patterns:** Referencia visual = print com fundo branco (12 filtros em dropdown expandivel)

### Performance
- Filtro por tags usa subquery: `WHERE contact_id IN (SELECT contact_id FROM contact_tags WHERE tag_id IN (...))`
- Filtro por campo personalizado usa containment: `.contains('custom_fields', { key: value })`
- Indices compostos essenciais para evitar full table scan

### Dependencias
- **Pre-requisito:** Story 1.1 (Tag System) — tabelas `tags` e `contact_tags` devem existir
- **Tabela `campaigns`** deve existir no schema (verificar migration init)

### Testing
- Testar cada filtro individualmente
- Testar combinacao de 3+ filtros simultaneos
- Testar filtros com resultados vazios (graceful empty state)
- Testar persistencia na URL (reload mantem filtros)
- Testar performance com dataset simulado
